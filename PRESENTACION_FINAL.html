01

Planteamiento

Por qué Oracle, si ya teníamos MongoDB

Lo que ya teníamos El backend original, apoyado en MongoDB, era ágil: cada producto, pedido o cuenta se resolvía con un documento y el equipo avanzaba sin migraciones. Agregar un campo era editar ese documento, no alterar toda la colección.

Lo que nos faltaba Cuando llegaron las reglas estrictas —stock que no puede quedar negativo, precios que no admiten valores inválidos, cada cambio auditado— necesitábamos la robustez de un motor relacional que impusiera esas reglas por sí mismo. Eso es lo que aporta Oracle, no la buena voluntad del código.

MongoDB flexibilidad

02

Base documental

El modelo NoSQL y su CRUD

En MongoDB todo se guarda como documento JSON: un producto es un objeto con sus nueve campos y un pedido lleva sus ítems dentro, así que se lee completo en una sola consulta, sin unir tablas. El backend hace el CRUD con el driver oficial: crear con insertOne, leer con find y findOne, actualizar con findOneAndUpdate y borrar con findOneAndDelete.

colección products · un documento
// db.products.findOne({ id: "prod-guantes-01" })
{
  "id":          "prod-guantes-01",
  "name":        "Guantes de Nitrilo M (caja 100)",
  "sku":         "GUA-001",
  "description": "Caja de 100 unidades, sin polvo.",
  "price":       8990,
  "category":    "Insumos",

  "image":       "/img/guantes.jpg"
}

Seis colecciones en la base medistock: products, users, orders, bank_accounts, bank_transactions y stock_alerts. Cada una declara su validador $jsonSchema y sus índices: únicos sobre id y sku, y en orders por customerId + createdAt.

CRUD a través del backend

  • CREATEinsertOne() con el documento ya validado por el $jsonSchema.
  • READfindOne() por la clave id; find() con proyección que excluye _id y orden explícito.
  • UPDATEfindOneAndUpdate() con $set: solo los campos enviados; lo ausente no se borra.
  • DELETEfindOneAndDelete(), que devuelve el documento eliminado para confirmar qué salió.

Rutas → servicios → repositorios → driver: las rutas nunca hablan con el driver. Además, cada escritura encola un evento en oracle_sync_outbox, y ese evento es exactamente el JSON que consume Oracle.

03

Réplica relacional · esquema C##MEDISTOCK

MED_PRODUCTOS en Oracle

Oracle no inventa nada: recibe lo que MongoDB escribe y lo ordena en tablas, con clave primaria en cada fila y claves foráneas donde hay relación. Esa estructura es la que permite las consultas agregadas y las auditorías —el valor del inventario, el historial de cada cambio de stock— sin cargar al frontend, que sigue leyendo de MongoDB.

Relación con pedidos

1 : N

MED_PEDIDOS 1 — N MED_DETALLE_PEDIDOS N — 1 MED_PRODUCTOS. El detalle tiene clave primaria compuesta (ID_PEDIDO, NUMERO_LINEA) y referencia el producto: así un producto aparece en muchos pedidos y cada línea guarda CANTIDAD y PRECIO_UNITARIO.

Solo dos FK son constraints reales: detalle → pedidos y transacciones → cuentas. Las demás son referencias lógicas que mantiene el paquete de sincronización, porque las tablas se cargan con MERGE y el orden de llegada no está garantizado.

04

El corazón del proyecto

La lógica PL/SQL completa

Este es el núcleo del trabajo: la lógica que la base ejecuta por sí sola. El paquete MEDISTOCK_GESTION reúne las funciones y procedimientos que consultan y actualizan el inventario; el VARRAY permite enviar una lista de pedidos en una sola llamada, sin repetir el procedimiento N veces; y los triggers vigilan cada fila para que ninguna operación rompa las reglas, venga de donde venga.

  • 01
    T_IDS_PEDIDO type

    VARRAY(100) OF VARCHAR2 a nivel de esquema: un parámetro de procedimiento no puede usar un tipo declarado dentro de un bloque.

  • 02
    MEDISTOCK_GESTION package
    • VALOR_INVENTARIO() — suma PRECIO × STOCK: 821.200
    • PRODUCTOS_BAJO_MINIMO() — cuenta los productos críticos: 2
    • MARCAR_PEDIDOS_ENVIADOS(VARRAY) — recorre el VARRAY y actualiza cada pedido
    • REGISTRAR_PRODUCTO() — excepción propia ORA-20010 si el precio es negativo
    • LISTAR_STOCK_BAJO() — RECORD + cursor explícito
    • MOSTRAR_PEDIDOS_POR_CATEGORIA() — cursores anidados parametrizados
  • 03
    MED_PRODUCTOS_STOCK_VALIDA_TRG trigger

    BEFORE INSERT OR UPDATE OF STOCK, por fila: rechaza stock negativo con ORA-20003.

  • 04
    MED_PRODUCTOS_STOCK_AUD_TRG trigger

    AFTER INSERT OR UPDATE OF STOCK: escribe en MED_HISTORIAL_STOCK el stock anterior y el nuevo. 17 cambios registrados en la prueba.

El paquete delega en los objetos sueltos FN_VALOR_INVENTARIO y PR_MARCAR_PEDIDOS_ENVIADOS en lugar de duplicar la lógica: una regla, una implementación, dos formas de invocarla.

trigger de validación · código real
CREATE OR REPLACE TRIGGER MED_PRODUCTOS_STOCK_VALIDA_TRG
BEFORE INSERT OR UPDATE OF STOCK ON MED_PRODUCTOS
FOR EACH ROW
BEGIN
  IF :NEW.STOCK < 0 THEN
    RAISE_APPLICATION_ERROR(-20003,
      'Stock invalido (' || :NEW.STOCK || ') para el producto '
      || :NEW.SKU || '. El stock no puede ser negativo.');
  END IF;
END MED_PRODUCTOS_STOCK_VALIDA_TRG;

05

Integración

De un documento JSON a una fila Oracle

El backend de Node.js serializa el documento y lo envía como JSON con tres datos: la entidad afectada, la acción y el contenido. El paquete MEDISTOCK_SINCRONIZACION lo recibe y hace un UPSERT: si el identificador no existe inserta la fila; si ya existe, la actualiza. Así el mismo procedimiento cubre altas y modificaciones.

Origen MongoDB documento products
stock: 25
Backend Node.js oracledb · 3 binds
JSON → CLOB
PL/SQL MEDISTOCK_SINCRONIZACION APLICAR_CAMBIO(
  entidad, accion, datos)
Destino MED_PRODUCTOS MERGE · fila replicada
PASO 01

El backend serializa

Node toma el documento y envía solo los campos de negocio como JSON, con p_entidad, p_accion y p_datos.

PASO 02

PL/SQL extrae y compara

El paquete lee el JSON con JSON_VALUE y JSON_TABLE, y ejecuta un MERGE contra la tabla destino.

PASO 03

Un solo camino para todo

Si el identificador existe, actualiza; si no, inserta. El mismo procedimiento sirve para alta y modificación.

llamado desde Node
BEGIN MEDISTOCK_SINCRONIZACION.APLICAR_CAMBIO(
  :p_entidad, :p_accion, :p_datos
); END;
resultado del UPSERT
-- 1ª ejecución: ID nuevo  → INSERT
-- 2ª ejecución: mismo ID  → UPDATE (+10 stock)
Tiempo PL/SQL 21 ms · Commit realizado

07

Cierre

Lo que aprendimos

01 — INTEGRIDAD

Una regla que la base impone

El trigger convierte una validación en algo que no depende de que el código se acuerde. Un stock de -5 no entra, venga de donde venga: lo comprobamos con ORA-20003 y con la fila que nunca se creó.

02 — AUTOMATIZACIÓN

La lógica vive en la base

Una función y un paquete evitan que cada cliente reimplemente el cálculo. El mismo VALOR_INVENTARIO responde a SQL, a Node o a un reporte: 821.200 CLP calculados en un solo lugar.

03 — ARQUITECTURA HÍBRIDA

Cada motor en lo suyo

MongoDB aporta el documento que cambia; Oracle, la fila que se audita. La sincronización en un solo sentido mantiene una verdad única y verificable, sin dos fuentes peleando por el mismo dato.
